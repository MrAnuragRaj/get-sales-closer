## Architecture Patterns

### Auth Guard
All protected pages: `requireAuth({ onAuthenticated: (profile, user, sb) => {} })`
- Requires: `<script src="auth.js">`, `<div id="auth-loader">` (visible), `<div id="page-content">` (hidden)
- Role pages (`agency_admin.html`, `enterprise_admin.html`, `agent_dashboard.html`) need `requireOnboarding: false`
- Exception: `pricing.html` + `payment.html` use inline auth-loader pattern (no auth.js)
- `consent.html` uses `requireOnboarding: false` — must never trigger onboarding redirect loop
- Step order in auth.js: 1 session check → 2 profile fetch → 3 onboarding gate → **4 pending-consent check** → 5 watchdog → 6 onAuthenticated

### Legal Consent Flow
**New users** — consent wall is step 0 of setup-modal in `dashboard.html`:
- `initConsentStep(userId, sb)` called via `onOnboarding` callback in `requireAuth()`
- Each doc shown in iframe (Google Docs Viewer); checkbox unlocks only when user scrolls to bottom of `#onb-modal-inner`
- Consents recorded to `onboarding_consents`; then proceeds to step 1 (phone/email/company) and step 2 (AI test drive)

**Existing users** — `auth.js` step 4 intercept:
- Checks active docs vs user's consent records; if any version mismatch → `window.location.replace('consent.html?return=<encoded_path>')`
- `consent.html`: full-page, scroll on `window`, upserts to `onboarding_consents`, redirects back via `?return=` param

**Admin document management** — Consent Documents section in `admin.html`:
- Table of all docs with consent count, status, view link, activate/deactivate toggle
- Upload form: title, description, version, display_order, file → uploads to `legal-docs` bucket → saves to `onboarding_consent_docs`
- Activating a new version automatically triggers re-consent for all existing users on next login

### Priority Intake Routing
- `leads.priority` column: `'standard'` (default) / `'high'`
- `fetch_due_tasks` RPC: orders by `CASE WHEN l.priority = 'high' THEN 0 ELSE 1 END, scheduled_for ASC` (LEFT JOIN leads)
- `execution_planner`: ALL leads (including high-priority) use `computeStrikeTime()` — TCPA contact window applies to automated systems regardless of consent
- High-priority advantage: compressed retry intervals (`getRetryScheduleHighPriority`) + queue ordering
- Off-hours human alert: when `isHighPriority && !isWithinContactWindow()` → SMS (Twilio) or email (Resend) sent to closer immediately — TCPA does NOT restrict human-initiated calls; alert is best-effort (never blocks task creation); in-app `notifications` row also inserted (`type: 'priority_off_hours'`)
- UI: priority pill badge on lead cards in dashboard.html + agent_dashboard.html; `lap-priority-off/on` toggle panel in lead action panel

### Token System
- Voice: 5 tokens pre-debit → settled via `settle_voice_call_tokens_v2`
- SMS/Email/WA/RCS/Messenger: 1 token each → `consume_tokens_v1(p_idempotency_key: task_id)`
- Refund on failure: `grant_tokens_core_v1`
- `consume_tokens_v1` reads `token_wallets` (runtime layer) — NOT `credit_wallets` (display layer)

### Executor Guard Order (frozen)
`platform kill switch → org kill switch → org cancellation → rate limit → channel capability → binding/fallback resolution → token/billing → delivery_attempt INSERT (idempotency 23505 guard) → send → delivery_attempt UPDATE`

### Human Takeover Flow
1. Agent clicks "Takeover" → `leads.ai_paused = true`
2. Agent types → `execution_tasks` with `metadata.force_content = text`
3. `executor_sms` detects `force_content` → skips AI, sends directly
4. Agent clicks "Resume AI" → `leads.ai_paused = false`

### Credit Purchase — doctor_report Special Case
`fulfill-paid-order` must call **both** `credit_wallet_add_v1` (display layer) **and** `grant_tokens_core_v1(scope='org')` for `doctor_report`. `consume_tokens_v1` reads `token_wallets` — if only `credit_wallets` is updated, quota appears added but generation fails at quota check.

## Lead Generation Engine (LGE) — Approved Architecture

**Service key:** `lead_gen` | **Status:** Sessions 1 + 2 complete — full pipeline live (worker running via pg_cron #19 every 2 min)
**Purpose:** Customer-facing — each GSC org uses LGE to find and qualify their own leads, then push high-score leads into GSC for immediate AI conversion.

**Pipeline:**
```

  → lge_ingest (edge fn)
  → lge_raw_leads (status: pending)
  → lge_worker (pg_cron every 2 min, FOR UPDATE SKIP LOCKED, batch 10)
  → Enrichment: Apollo API → Hunter email verify (customer's own API keys)
```

- hook_inbound stays untouched — LGE passes `source='lge'`, metadata in notes as JSON; no LGE-specific parser added

- LGE leads are separate from GSC leads until pushed — prevents polluting conversion pipeline

- LinkedIn: never — ToS violation, legal risk, no stable API

14. **Growth Engine Founder Dashboard**: calls `admin_get_growth_metrics` + `admin_get_beta_prospects` in `Promise.all` — both require `profiles.is_admin = true` on the caller; will silently return empty if called as non-admin
15. **`create_checkout_intent` pricing (version 4)**: Two DB overloads — 2-param (old, `intent_source` in `'checkout'|'upgrade'`) and 3-param (current, `intent_source` in `'pricing'|'billing'`). pricing.html and billing.html use the 3-param version. Correct prices: intake=$149, safe_voice=$199, priority=$99, chatbot=$149, install=$99 (one-time), growth_engine=$660. Channel model for S-alone: `base = 49 + max(0, (sms+wa+fb count - 1) * 10)`. 17. **Growth Engine FastAPI — asyncpg jsonb**: asyncpg does NOT auto-serialize Python dicts for jsonb columns. Always `json.dumps(your_dict)` before passing as a query parameter.
18. **Growth Engine FastAPI — JWT auth**: `org_members` has no `created_at` column. Never add `om.created_at` to ORDER BY in auth_bridge.py or oauth routes. ES256 JWTs must only use JWKS (`_get_jwks_client()`), never HS256 — inspect the JWT header `alg` claim first.

20. **`consent.html` must use `requireOnboarding: false`** — otherwise users with `onboarding_completed = false` get stuck in a redirect loop between auth.js onboarding gate and consent.html.
21. **Priority Intake Routing — TCPA**: `computeStrikeTime()` applies to ALL automated tasks regardless of lead priority. High-priority leads do NOT bypass the 08:00–19:59 contact window. Off-hours alert goes to the *closer* (not the lead) — this is an internal operational alert, not a marketing message, so TCPA automated-dialer restrictions don't apply.

23. **Consent scroll detection — modal vs window**: New-user consent (setup-modal) detects scroll on `#onb-modal-inner` div. Existing-user consent (`consent.html`) detects scroll on `window`. Never mix them up — the modal is a scrollable div inside a fixed overlay; `window.scrollY` won't fire there.
24. **`crm_escalations` column is `priority` not `severity`** — CHECK constraint values: `critical/high/medium/low`. Any function referencing `e.severity` will fail with 42703.
25. **`crm_contact_ownership` has no `user_id` column** — layered ownership uses `primary_owner_id`, `supporting_owner_id`, `escalation_owner_id`, `cs_owner_id`. Focus Mode filter must check: `p_user_id IN (o.primary_owner_id, o.supporting_owner_id, o.escalation_owner_id, o.cs_owner_id)`.
26. **`crm_predictive_scores.churn_drivers` is a JSONB array** (not object) — use `jsonb_array_elements()` not `jsonb_each_text()`. Column is `churn_drivers`, not `churn_probability_drivers`.
27. **`crm_predictive_scores.engagement_momentum` is TEXT** (`'improving'/'stable'/'declining'`), not INT — never compare with `> 5` or `< -5`; use `CASE ps.engagement_momentum WHEN 'improving' THEN ...`.
28. **`get_crm_command_center` overload history** — Phase 11 created 1-param `(UUID)`, Phase 11 Refinements created 2-param `(UUID, UUID DEFAULT NULL)`. Both coexisted causing PGRST203. Fixed in migration `20260521_fix_command_center_overload.sql` by dropping the 1-param version. Never recreate the 1-param overload.
29. **`crm_predictive_scores.expires_at` TTL is 48 hours** (not 7 days) — freshness derivation in native_crm.html uses `expires_at - 7d` as `scored_at` proxy, which is incorrect. Actual formula: `scored_at ≈ expires_at - INTERVAL '48 hours'`. Low impact until predictive scores are densely populated.
30. **Management API PAT expires** — The PAT in `memory/supabase-access.md` (`sbp_d927ee7a...`) expired as of this session. To run arbitrary SQL, use the Supabase Dashboard SQL Editor directly. The service role key (JWT) remains valid until 2084.
31. **`crm_relationship_maturity` has no `days_in_stage` column** — `GENERATED ALWAYS AS (EXTRACT(DAY FROM now() - entered_at))` is not immutable in PostgreSQL. Use `EXTRACT(DAY FROM now() - rm.entered_at)::INT` inline in queries. The `get_crm_relationship_intelligence` RPC computes this inline as `maturity_days_in_stage`.
32. **`crm_activities` date column is `occurred_at`** — Not `activity_date`. Inbound/outbound direction uses the `direction` column (`'inbound'`/`'outbound'`), not `activity_type` string matching.
33. **Sprint 2 initial trust distribution is expected** — After fresh import, 99% of contacts show `trust_state='strained'` because `relationship_capital_score < 35` (new contacts have 0 activities, avg capital ~15–25). This is correct behavior — it signals "no relationship capital built yet", not a trust crisis. Capital will grow as activities are logged and pg_cron runs nightly.
34. **`capital_velocity` is always 0 on first nightly run** — velocity = new_cap - old_cap. On the very first execution after the column is added, old_cap equals the value already stored, so delta = 0. Velocity will diverge meaningfully from the second nightly run onwards as activity changes.
35. **Trust hysteresis: recovery requires time-gating** — After R1 refinements, the compute function's ELSE clause preserves `c.trust_state` (not `'intact'`). A strained contact with capital ≥65 will NOT recover to rebuilt until `trust_changed_at <= now() - INTERVAL '7 days'`. In tests, manually set `trust_changed_at = now() - INTERVAL '8 days'` to verify recovery logic.
36. **`crm_relationship_principles` trigger_condition JSONB** — The `get_crm_applicable_principles` RPC evaluates these fields: `trust_states[]`, `relationship_states[]`, `lifecycle_stages[]`, `strategic_tiers[]`, `min_capital_score`, `max_capital_score`, `min_churn_probability`, `min_days_silent`. Any absent key is treated as "no constraint". Manually added principles (evidence_source='manual') use `{}` for universal applicability.
37. **`esc()` vs `escHtml()`** — native_crm.html uses `esc(s)` as the HTML escape utility (defined in the Utilities section). Do not add `escHtml()` — it doesn't exist. The Sprint 3 principle rendering uses `esc()`.
38. **`crm_resilience_snapshots` initial values are high by design** — Fresh-import contacts with no fractures, no escalations, and zero volatility score resilience_index=80 (recovery=12 + recurrence=25 + stability=25 + sensitivity=18). reciprocity_score=100 (inbound_ratio=50 fallback for <3 activities → `100 - ABS(50-50)*2 = 100`). These will diverge meaningfully as fractures are logged and activities accumulate.
39. **`compute_crm_resilience_scores` activity direction** — reciprocity uses `a.direction = 'inbound'` from `crm_activities`. The inbound_ratio falls back to 50 when total_activities < 3 (insufficient signal). reciprocity_score = `GREATEST(0, 100 - ABS(50 - inbound_ratio) * 2)` — peaks at 50% inbound (score=100), zero at 0% or 100% inbound (score=0).
40. **Pre-Sprint 4 principle columns** — `crm_relationship_principles` now has: `contradiction_count`, `last_confirmed_at`, `last_reinforced_at`, `reinforcement_trend` (improving/stable/declining/unknown), `confidence_decay_rate` (0–5 per week), `scope_type` (org_wide/vertical/account/owner/tier), `scope_target` (UUID or string), `memory_class` (foundational_truth/emerging_pattern/weak_signal/temporary_behavior/contested_heuristic). `is_stale` is a derived boolean: `last_reinforced_at < now() - INTERVAL '90 days' AND confidence_decay_rate > 0`.
41. **`resilience_index` includes fracture_accumulation_penalty** — After pre-Sprint 5 refinements, the final `resilience_index` = sum of 4 components MINUS `fracture_accumulation_penalty`. A contact with 6+ total fractures takes a -25 penalty even if individual recovery scores are high. Fresh-import contacts still score ~80 (no fractures = 0 penalty). The penalty makes repeated damage degrade resilience nonlinearly.
42. **`reciprocity_trend = 'stable'` on first run after refinements** — Because `prev_inbound_ratio` is read from the previous snapshot before the INSERT, on the first refresh after the column is added, old_ratio = same as new_ratio (both from the already-stored 50). Trend will show 'stable' correctly. Meaningful divergence (improving/declining) starts once activity patterns change between runs.
43. **`crm_account_resilience` keyed on `company_name` text** — Not a UUID. Matching is exact case-sensitive text. If a contact's `company` field has inconsistent casing ("Acme" vs "acme"), they appear as separate accounts. Normalize company names in imports to avoid fragmentation.
44. **`compute_crm_sprint5_nightly` is the pg_cron #59 target** — It calls `compute_crm_maintenance_burden` then `compute_crm_account_resilience` in sequence. If you need to run maintenance compute independently, call `compute_crm_maintenance_burden(p_org_id)` directly. Account resilience depends on `crm_contacts.maintenance_burden` being current, so always run maintenance first.
45. **`crm_relationship_snapshots` needs 2+ rows per contact for inflection detection** — `detect_crm_inflection_points` runs LAG over consecutive snapshots. On the first pg_cron run, only one snapshot exists (from the migration's initial DO block) so no inflections are written (this is correct). Inflections start appearing from the second nightly run onwards.
46. **`relationship_outlook` lives on `crm_relationship_snapshots`, NOT `crm_contacts`** — There is no `relationship_outlook` column on `crm_contacts`. The info grid and trajectory panel both read it via `get_crm_relationship_trajectory` RPC (loaded by `loadRelationshipTrajectory`). If no snapshots exist yet, the Outlook cell shows "No data".
47. **`maintenance_efficiency_score = 100` when burden = 0** — The efficiency formula uses `NULLIF(burden, 0) * 50` in the denominator. When burden is 0 (fresh-import contacts), the fallback branch returns 100. This is correct: zero burden = maximum efficiency regardless of value score.
48. **`burden_velocity = 0` on first run after Sprint 6 migration** — Same pattern as `capital_velocity`: the previous snapshot was just written, so old_burden = new_burden → delta = 0. Velocity diverges from the second nightly run onwards.
49. **`trajectory_confidence = 'sparse'` on first few nightly runs** — `compute_crm_trajectory_confidence` needs ≥7 snapshots for 'moderate', ≥30 for 'confident'. Fresh orgs show 'sparse' for the first 6 days (one snapshot per pg_cron #60 run). Narrative shows "Insufficient trajectory data yet — check back after a few nightly cycles." This is correct.
50. **`trajectory_acceleration` requires 3 snapshots (2 consecutive deltas)** — On the 1st and 2nd nightly run, only 1–2 snapshots exist; `delta2` will be 0 (LEFT JOIN miss), so acceleration defaults to 'steady'. Meaningful acceleration values emerge from the 3rd run onwards.
51. **`crm_expansion_opportunities` 14-day TTL** — `detect_crm_expansion_opportunities` deletes expired rows first (`expires_at < now()`), then upserts fresh ones (`ON CONFLICT DO UPDATE`). After a nightly compute gap >14 days, all opportunities disappear until the next run. Freshly seeded orgs will have no opportunities until pg_cron #61 runs.
52. **`compute_crm_sprint7_nightly` run order matters** — It calls `compute_crm_loyalty_scores` first, then `detect_crm_expansion_opportunities`, then `compute_crm_expansion_refinements`. Refinements read `loyalty_score`, `advocacy_score`, `expansion_readiness_score`, and `churn_probability` — all must be current. Never reverse or skip steps.
53. **`expansion_confidence` defaults to 50 until first nightly run** — `compute_crm_expansion_refinements` populates `expansion_confidence`, `advocacy_resilience`, `growth_strain_detected`, and `expansion_narrative`. Until pg_cron #61 completes, contacts show 50/50/false/null. The initial DO block in the Pre-Sprint 8 migration runs the function immediately for all active orgs.
54. **`first_detected_at` on `crm_expansion_opportunities` is set on INSERT only** — The ON CONFLICT DO UPDATE clause deliberately excludes `first_detected_at`. If `detect_crm_expansion_opportunities` runs nightly and finds an existing opportunity, it updates urgency/confidence/evidence but preserves the original detection timestamp. This enables opportunity aging display.
55. **`crm_portfolio_snapshots` climate_state uses percentage thresholds not counts** — `expanding` requires improving_pct ≥30 AND critical_pct <10 AND expansion_ready/total ≥20%. Fresh orgs with no relationship snapshots (outlook distribution all NULL) will default to 'stable'. Climate becomes meaningful after Sprint 6 snapshots accumulate (7+ days).
56. **`crm_concentration_risks` is UNIQUE per org** — ON CONFLICT (org_id) DO UPDATE. A single row per org, overwritten nightly. With small contact lists (< 10 contacts), top-3 concentration will naturally be 50–100% — this is mathematically correct, not a bug. Concentration risk only becomes operationally meaningful at 30+ contacts.
57. **`compute_crm_sprint8_nightly` must run after sprint7** — pg_cron #62 (05:30 UTC) runs after #61 (05:00 UTC). Portfolio snapshot reads `expansion_readiness_score`, `growth_strain_detected`, `advocacy_score` from crm_contacts — these must be current. Never schedule #62 before #61.
58. **`generate_crm_relationship_briefing` is on-demand, not nightly** — No pg_cron job. Triggered from the Generate Briefing button per contact. The function upserts on UNIQUE(org_id, contact_id), so regenerating overwrites the previous briefing. The JS `_briefingCache` holds the latest briefing for the current session only.
59. **`crm_relationship_briefings` signals column uses `churn_drivers` column name from crm_contacts** — The signals JSONB snapshot reads from `crm_predictive_scores.churn_probability` / `expansion_probability` (not from crm_contacts). These may be NULL if pg_cron #49 has not yet run. All signal values default to 0 or 'unknown' if predictive scores are absent — briefing renders cleanly.
60. **`climate_acceleration` requires 3 portfolio snapshots** — `compute_crm_portfolio_snapshot` uses `OFFSET 1` to get the snapshot two days before current, enabling two consecutive avg_capital deltas. On the first two nightly runs, `prev_prev_capital` is NULL (LEFT JOIN miss), so acceleration defaults to 'stable'. Meaningful 6-value acceleration appears from the 3rd run.
61. **`portfolio_fragility_index` reads top-3 expansion contacts' resilience_index** — The fragility computation joins `crm_concentration_risks.top_expansion_contacts` JSONB (array of contact_ids) back to `crm_contacts.resilience_index`. If resilience hasn't been computed yet (pg_cron #58 not run), avg_resilience defaults to 50, so fragility_index = top3_pct × 0.5. Expected on fresh orgs.
62. **`expansion_fatigue_days` is always 0 the first time `detect_crm_expansion_opportunities` runs** — On the initial run, `first_detected_at = now()` for all new opportunities. `compute_crm_expansion_refinements` then reads `MIN(first_detected_at)` from active opportunities — all are 0 days old. Fatigue first appears 21+ days after initial detection. Never backdate `first_detected_at` manually.
63. **`detect_crm_signal_drift` requires ≥2 snapshots separated by ≥6 days** — It compares the latest snapshot to the closest snapshot that is at least 6 days old. Contacts with only 1 snapshot (freshly imported orgs) are silently skipped — no error, no drift event. Meaningful drift detection begins after 7+ daily nightly cycles.
64. **`crm_signal_drift_events` UNIQUE(contact_id, signal_name, detected_date)** — Running `detect_crm_signal_drift` multiple times on the same day for the same org is safe — ON CONFLICT DO NOTHING. The pulse computation always reads the last 7 days, so same-day re-runs are idempotent.
65. **`briefing_confidence='low'` on fresh orgs** — If `crm_predictive_scores` has never been computed (pg_cron #49 not run) or relationship snapshots are absent, `v_pred_age_hours = 999` → confidence immediately drops to 'low'. This is correct behavior — a briefing with no predictive data is genuinely low-confidence. The freshness note will state the specific missing source.
66. **Signal contradictions fire on static thresholds, not deltas** — The contradiction detection in `generate_crm_relationship_briefing` reads current column values (e.g. `advocacy_score >= 65 AND maintenance_burden >= 65`). It does not compare vs historical values. A contradiction can persist across multiple briefing regenerations if the underlying signal state doesn't change.
67. **`compute_crm_portfolio_health_pulse` pg_cron #64 must run after #63** — The pulse aggregates drift events from the last 7 days. If #63 (drift detection at 06:00) hasn't run, the pulse will be based on the previous day's events only. Always schedule #64 at least 10 minutes after #63.
68. **`crm_roles` is per-org, not global** — Even system roles (is_system=TRUE) are seeded once per org via `ensure_crm_system_roles_seeded`. This function is idempotent (ON CONFLICT DO NOTHING) and is called lazily from `check_crm_permission` and `get_crm_user_roles`. Never call it more than needed in hot paths.
69. **`crm_governance_audit` has no UPDATE/DELETE RLS policy** — Only a SELECT policy exists. Rows are written exclusively via SECURITY DEFINER RPCs (`assign_crm_user_role`, `revoke_crm_user_role`, `update_crm_contact_sensitivity`). Never expose INSERT to client JS directly — the immutability guarantee depends on it.
70. **`check_crm_intelligence_health` uses `updated_at` then falls back to `expires_at - 48h`** — `crm_predictive_scores` may not have `updated_at` if the column was named `scored_at` in earlier migrations. The function gracefully falls back. If both are NULL, pred_age_h = 9999 → status = 'missing'.
71. **`sensitivity_level` defaults to `'normal'`** — The CHECK constraint rejects any other string. The `update_crm_contact_sensitivity` RPC validates client input before UPDATE and returns `{success: false, error: 'Invalid sensitivity level'}` on bad values. The badge is hidden when level = 'normal' (shows only when elevated).
72. **`crm_signal_provenance` is write-only from application layer** — No automated writes in Sprint 11; the table is a declared infrastructure for future compute layers to emit provenance records. The `log_crm_signal_provenance` convenience RPC can be added in Sprint 12+ when intelligence layers start writing to it.
73. **Role assignment modal populates members via `org_members` JOIN `profiles`** — The join uses `profiles(full_name, email)` which requires the `profiles` table to be accessible. If a member has no profile row, their user_id is shown as a fallback. This is a display issue only and does not break role assignment.
74. **Sprint 12 functions: `crm_contacts.name` not `full_name`** — The contacts table uses `name` (single column), never `full_name`. All executive review RPCs use `c.name`.
75. **Sprint 12: churn/expansion probabilities are on `crm_predictive_scores`, NOT `crm_contacts`** — Always JOIN `crm_predictive_scores cps ON cps.contact_id = c.id` and use `cps.churn_probability` / `cps.expansion_probability`. The columns do not exist on `crm_contacts`.
76. **Sprint 12: `crm_signal_drift_events.delta` not `delta_value`** — The drift delta column is named `delta` (INT). Columns: `id, org_id, contact_id, signal_name, direction, old_value, new_value, delta, severity, detected_date, detected_at`.
77. **Sprint 12: `crm_predictive_score_history` has NO `churn_score_delta`** — That is a GENERATED column on `crm_predictive_scores` (the live scores table). The history table columns are: `id, contact_id, org_id, snapshot_date, churn_probability, expansion_probability, renewal_probability, referral_likelihood, revenue_trajectory, engagement_momentum, revenue_momentum, relationship_momentum, computed_at`.
78. **`_execReviewCache` is a date-keyed object** — `{[dateStr]: reviewData}`. Historical reviews are cached per date string (YYYY-MM-DD). `_execReviewDates` holds the list of available review rows (id, review_date, review_hash, prior_review_id, generated_at, signal_counts). `refreshExecReview()` overwrites today's entry. Historical reviews are NEVER regenerated — they are immutable snapshots.
79. **Historical reviews must be loaded from DB, not regenerated** — When a user selects a past date in the Executive Review modal, `loadExecReviewFromDB(dateStr)` reads from `crm_executive_reviews` directly. Never call `generate_weekly_exec_review` for past dates — it would overwrite the stored snapshot with recomputed modern intelligence.
80. **`recoverability` classification hierarchy (5-state, evaluated in order)**: terminal → structurally_broken → escalation_dependent → fragile → recoverable. Conditions: terminal = trust broken + churn ≥80 + capital_velocity ≤0 + resilience <40; structurally_broken = trust broken + churn ≥60 + trajectory collapsing/deteriorating; escalation_dependent = active critical/high escalation + churn ≥60; fragile = churn ≥60 + capital_velocity <0 + resilience <50; recoverable = all else.
81. **`review_hash` is a deterministic md5 of 4 metrics** — `md5(worsening_count | improving_count | critical_esc | worsening_accounts_count)`. Used for future delta comparison. The first 8 chars are shown in generation metadata as a visual fingerprint.
82. **`cognitive_load_level = 'light'` expected on fresh import** — All 5 load components default to 0 without operational data (0 volatility, 0 signal conflicts, 0 maintenance burden, 0 roles, no trajectory deterioration). Meaningful cognitive load only appears after Sprint 2/5/6 nightly cycles accumulate 7+ days of activity data.
83. **`crm_operator_fatigue` requires `crm_contact_ownership` entries** — Fatigue is computed per `primary_owner_id` in `crm_contact_ownership`. If no owners are assigned, `get_crm_operator_fatigue` returns 0 operators and empty list. The Operator Sustainability panel correctly shows "No operator assignments found" in this case.
84. **Queue clusters require thresholds: churn_cohort ≥80% needs 2+ contacts; escalation_cluster needs 2+ contacts with critical/high priority; deterioration_wave needs 4+ contacts with capital worsening drift in 7d; fatigue_cluster needs 4+ contacts with burden ≥60; expansion_cohort needs 3+ contacts with readiness ≥65 and no growth strain.** — On fresh orgs with no predictive scores or escalations, all cluster queries return 0 rows (HAVING filters). This is correct — clusters appear after pg_cron #49 (predictive) and #63 (drift) cycles.
85. **`crm_signal_suppression` partial index on `suppressed_until`** — The partial WHERE clause `WHERE suppressed_until > now()` was rejected by PostgreSQL (IMMUTABLE violation). The fallback full index `idx_crm_signal_suppression_org` on `(org_id, suppressed_until DESC)` was created instead. All queries that filter on `suppressed_until > now()` will correctly use this index for range scans.
86. **`attention_load` in `generate_weekly_exec_review`** — Score formula: `escalation_pressure = MIN(critical_esc×15, 30)` + `deterioration_spread = MIN(worsening_accts×5, 25)` + `drift_pressure = MIN(MAX(worsening-improving,0)×3, 20)` + `fatigue_load = MIN(fatigue_accts×5, 15)` + `climate_penalty = 10 if climate in ('contracting','cooling')`. Level: light 0-25 / moderate 26-50 / heavy 51-75 / critical 76+. Stored in `crm_executive_reviews.attention_load JSONB`.
87. **`recovery_blocker` evaluated before `primary_recovery_driver` in rendering** — When a blocker exists, it shows with a warning triangle (▲ color) and the driver shows as muted (▼ opacity-60). When no blocker exists, only the driver shows. This visual hierarchy prevents confusing "rising capital" driver messages from overshadowing a "trust fracture" blocker.
88. **`crm_attention_debt_snapshots` initial debt_score=0 is correct** — On fresh orgs with no escalations, no churn clusters, no stale opportunities, and no suppression, all 6 debt components are 0. Debt_level='healthy', debt_velocity='stable'. Meaningful debt emerges after 2+ overnight pg_cron cycles where escalations accumulate unresolved.
89. **`compute_crm_queue_calmness` is stability-based, NOT volume-based** — High alert volume does not automatically produce a low calmness score. The function penalizes volatility (cluster_count change), escalation churn (new vs resolved), suppression density (ratio of active suppressions), fragmentation average across operators, drift acceleration, and cluster turnover. An org with high but stable load can score calm=70+. An org that destabilizes under moderate load scores turbulent/volatile.
90. **`calmness_score=100 - penalties` on fresh org** — All 6 penalty terms are 0 when no clusters exist, no escalations have fired, no suppression is active, operators are fresh, and no drift events exist. Score defaults to 100 (calm). Calmness degrades meaningfully after 2–3 nightly cycles with live operational data.
91. **`cluster_state='observed'` on first detection** — `compute_crm_queue_clusters` now sets `cluster_state='observed'` for all new clusters. Promotion to 'elevated' (first_seen_at > 7d + severity increasing) and 'escalated' (severity=critical + member count growing) happens on subsequent nightly runs. 'resolved' is set when the HAVING threshold is no longer met. Never manually set cluster_state — the compute function owns the state machine.
92. **`fragmentation_score=0` until operator owns mixed-state contacts** — Fragmentation is computed from `relationship_state_spread` (distinct relationship states across owned contacts), `escalation_priority_spread` (distinct priorities), and `cluster_diversity` (how many distinct cluster types the operator's contacts appear in). Fresh orgs with all contacts in 'strained' state have rs_spread=1 → fragmentation=0. Fragmentation rises as contacts diverge into active/loyal/at_risk/cooling states.
93. **`recovery_velocity='unknown'` until 2 consecutive fatigue snapshots exist** — Velocity is computed by comparing today's fatigue_score vs yesterday's. On the first nightly run after the pre-Sprint 14 migration, there is no prior row to compare against. The fallback returns 'unknown'. Meaningful velocity (improving/stable/worsening/accelerating) starts from the second nightly run.
94. **`regret_detected=FALSE` expected initially** — `check_crm_suppression_regret` only marks regret when a suppressed signal's contact subsequently develops a high/critical escalation, churn spike, or pulse worsening. Fresh orgs with no suppressions and no escalations will show 0 regrets. Regret detection requires the suppression system to have been running for at least 14 days (suppression TTL) before a meaningful regret signal can emerge.
95. **`crm_relationship_edges` is 0 rows on fresh orgs** — Edge detection requires roles assigned via `crm_contact_roles`. Without roles, `detect_crm_relationship_edges` produces no edges (all JOINS return empty). Influence scores default to 5 (min role_score), hub_type='standard', structural_fragility='stable'. Edges start appearing as users assign champion/economic_buyer/executive_sponsor/blocker roles to contacts.
96. **`champion_sponsor` edge direction is always a_to_b** — contact_id_a = champion, contact_id_b = economic_buyer/executive_sponsor. Inbound query reads contact_id_b = target. When rendering in `get_crm_contact_topology`, outbound_edges shows contacts the target champions toward; inbound_edges shows who is championing this contact.
97. **`peer_dependency` uses `r1.contact_id < r2.contact_id` guard** — This prevents duplicate bidirectional pairs (A↔B and B↔A stored as two rows). The UNIQUE constraint is on (org_id, contact_id_a, contact_id_b, edge_type) — so pair order matters. Always use LEAST/GREATEST when inserting bidirectional edges to ensure deterministic ordering.
98. **`isolation_node` detection requires strategic_tier** — A contact with ≤1 edge AND strategic_tier IN ('flagship','anchor','strategic_logo') becomes isolation_node. Standard-tier contacts with few edges stay 'standard'. Strategic accounts with no relationship edges are structurally dangerous — isolation_node classification is the correct signal.
99. **`compute_crm_sprint14_nightly` must run AFTER sprint13 nightly** — Sprint 14 reads `fatigue_score` and `cluster_state` from sprint 13 tables. pg_cron #sprint13 runs at 07:00 UTC; sprint14 at 07:15 UTC. Never swap the order.
100. **`get_crm_topology_summary` champion_concentration query requires ≥3 contacts per company** — The HAVING clause: `COUNT(*) FILTER (WHERE role_type='champion') = 1 AND COUNT(DISTINCT c.id) >= 3`. Accounts with 1 or 2 contacts are excluded even if they have a single champion. This prevents false positives on small accounts where single-champion is statistically expected.
101. **`crm_integrity_violations` has `first_seen_at`, `last_seen_at`, `repeat_count`** — Added by critic refinement. On INSERT: `repeat_count=1`, `first_seen_at=now()`. ON CONFLICT DO UPDATE: `repeat_count = old + 1`, `first_seen_at` preserved (NOT updated), `last_seen_at = now()`. The frontend shows a `Xd repeat` badge when `repeat_count > 1`. Violations that persist across multiple same-day reruns correctly accumulate count.
102. **`crm_integrity_violations` auto-resolves yesterday before each run** — `run_crm_integrity_checks` first UPDATEs all prior-day violations to `auto_resolved=TRUE`. Then re-inserts violations for today. If a violation persists (e.g., zombie escalation still open), it writes a fresh row for today's date. The partial index `WHERE NOT auto_resolved` means resolved violations don't affect query performance.
102. **`check_crm_intelligence_health` column `scored_at` does not exist** — `crm_predictive_scores` uses `computed_at` (not `scored_at`). The Sprint 15 migration was corrected to use `MAX(computed_at)`. If this function is ever recreated, never reference `scored_at` on this table — use `computed_at`.
103. **`crm_portfolio_health_pulse` pulse column is `pulse_date` not `snapshot_date`** — Every other time-series table uses `snapshot_date`; portfolio_health_pulse is the exception. The Sprint 15 health check and any query joining on pulse date must use `pulse_date`.
104. **`crm_operator_fatigue` date column is `computed_date` not `compute_date`** — Full column name: `computed_date DATE`. Any query casting to TIMESTAMPTZ: `MAX(computed_date)::TIMESTAMPTZ`. Do not use `compute_date`.
105. **`check_crm_intelligence_health` 13-layer sort order** — Layers are sorted worst-first: missing (age=NULL, sort=0) → stale (≥96h, sort=1) → degraded (≥52h, sort=2) → aging (≥28h, sort=3) → healthy (<28h, sort=4). Within each tier, sorted by layer name. The Intelligence Health panel renders them in this order so operators see the most critical issues first.
106. **`dependency_warnings` field changed format** — Sprint 15's `check_crm_intelligence_health` returns `dependency_warnings` as `JSONB array of objects {warning: TEXT}` (from `jsonb_build_object('warning', ...)`). Sprint 11 frontend expected plain strings. The `loadIntelligenceHealth()` function handles both: `typeof w === 'string' ? w : (w.warning ?? '')`.
107. **Integrity violations = 0 on fresh orgs** — On orgs with no escalations, no scores, no snapshots, all 8 checks produce 0 affected_count → no violation rows inserted. The panel correctly shows nothing. Violations accumulate meaningfully after 30+ days of operational use (zombie escalations, stale scores).
108. **Edge confidence explanation is deterministic from `evidence_sources.basis`** — The `edgeReason()` function in `loadContactTopology()` maps 4 basis values to human-readable strings. If `evidence_sources` is absent (e.g., older edges before the patch), the reason falls back to edge_type label. Both inbound and peer edges now include `evidence` in the `get_crm_contact_topology` response (patch migration `20260521c_sprint14_topology_evidence.sql`).
109. **`crm_contact_roles` column is `role` not `role_type`** — The Sprint 14 migration (`20260521_sprint14_relationship_topology.sql`) had `role_type` throughout `detect_crm_relationship_edges`, `compute_crm_influence_scores`, and `get_crm_topology_summary` but the actual column is `role`. Fixed in `20260521e_sprint14_role_column_fix.sql`. Also adds `evidence_sources.basis` field to each edge type so the frontend `edgeReason()` mapping works. Never reference `role_type` in queries against `crm_contact_roles`.
110. **`isolation_node` classification applies to contacts with ≤1 edge AND flagship/anchor/strategic_logo tier** — A strategic-tier contact that is the TARGET of edges only (inbound) counts edges in both directions. An executive_sponsor championed by one contact has edge_count=1 and qualifies as isolation_node if flagship tier. This is structurally correct: the contact has limited connectivity regardless of inbound/outbound direction. Expected on freshly hydrated orgs where edges are sparse.
111. **`get_crm_topology_summary` `structural_gaps` is per-contact, not per-company** — The query returns flagship/anchor/strategic_logo contacts that don't have the champion role THEMSELVES, grouped by company. If a company has a champion (Marcus) plus 3 non-champion flagship contacts, all 3 appear in structural_gaps. This is a coverage gap at the individual level, not a "company has no champion" gap. Do not confuse with champion_concentration (which measures single-champion accounts).
